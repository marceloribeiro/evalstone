The center is where evals become a **practice** shared by a team: the library on each
machine keeps running suites; the center keeps the history, the datasets, the human
labels, the judge calibrations and the production monitors in one PostgreSQL database,
behind one API and one web app.

## Attach a project

In `evalstone.yaml`:

```yaml
center:
  url: https://api.evalstone.com
  project: <project id>            # shown on the project's home page
  api_key_env: EVALSTONE_API_KEY   # an es_… ingest key minted on the project
```

From then on `evalstone run` pushes its report, judges run through the center's model
proxy with the organization's provider keys (no key on the machine), verdicts are cached
in the center, and `human` checks look labels up there. Prompt targets — the system under
test — still use your local `providers:`.

## What the web app shows

- **Project home** — the attach snippet, ingest keys, a live feed of events, the latest runs.
- **Runs** — every report pushed, per-check rates, the gate, every result with its reason,
  a diff against the suite's baseline (regressions and improvements, sample by sample).
- **Datasets** — immutable content-hashed versions, a sample viewer, the diff between two
  versions, tags.
- **Labeling** — queues to grade outputs, compare two runs A/B, or verify a dataset's
  expected answers; assignment; a keyboard-driven labeler (digits, P/F, A/B/T, S, Enter).
- **Judges** — the organization's providers (keys write-only), the project's judge
  settings, every judge version seen in results, calibrations against human labels
  (agreement, Cohen's kappa, confusion), and *Promote* to make a calibrated judge the
  check's model.
- **Monitors + alerts** — sampled production traces scored every minute with catalog
  checks, a windowed alert policy, a webhook, the traces themselves (flag the odd ones).
- **Check catalog** — checks defined once per organization from the library's built-in
  types, versioned, exported as the `checks:` block of an `evalstone.yaml`.
- **Members, invitations, project settings.**

## API

Everything above is a REST endpoint with OpenAPI docs (`/docs`, behind basic auth on
the hosted instance): organizations, projects, ingest keys, providers and judge
settings, the model proxy, datasets and versions, checks, runs and results, labels and
the judge cache, label queues, judges and calibrations, traces, monitors, alerts, and a
WebSocket per project for live updates. Users authenticate with a JWT; the library, CI
and proxies use a per-project ingest key.

## Stack

FastAPI · SQLAlchemy 2 + Alembic · PostgreSQL 16 with pgvector · Redis · Celery for
calibration jobs and monitor scoring · Next.js for the web app. One `docker-compose.yml`
runs all of it for self-hosters.
