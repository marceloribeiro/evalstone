The engineering roadmap lives in the repository and is the source of truth:
[docs/ROADMAP.md](https://github.com/marceloribeiro/evalstone/blob/main/docs/ROADMAP.md).

## Built

- Site + learning center (this site).
- **Library** — datasets, deterministic checks, targets, suites, runs, gates; judge
  adapters (OpenAI-compatible, Anthropic, Gemini); RAG, safety, pairwise and trajectory
  checks; CLI; the `rag-bot` sample. On PyPI since 2026-10-13; **0.2.0 (2026-10-14)**
  attaches a project to a center.
- **Integrations** — MCP server, pytest plugin and terminal labeling ship with
  the library; the GitHub Action is hosted in the repository
  (`marceloribeiro/evalstone/action@action-v0`).
- **Center API + web** — organizations, projects, datasets with versions, run history and
  diffs, the check catalog, labeling queues, judge calibration and promotion, monitors,
  alerts and traces, live updates over WebSocket. Self-host with `docker compose`, or use the
  hosted one at [app.evalstone.com](https://app.evalstone.com) (2026-10-14).

## Next, in order

1. Judged runs, a calibration and a promoted judge in the demo organization.
2. Email alerts next to the webhook.
3. Harvest traces into a dataset version with embedding dedup.
4. The library pulling the organization's `checks:` from the center at run time.
5. Bulk judge-cache warming and threshold-based judge promotion.

## Deferred

- TypeScript library (HTTP + MCP cover non-Python callers first).
- Fine-tuning execution (the iteration log tracks runs; it does not train weights).

## Follow along

Every commit, decision record and issue is public on
[GitHub](https://github.com/marceloribeiro/evalstone). Open an issue with the
eval problem you are stuck on; that is how the chapters get better.
